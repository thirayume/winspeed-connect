# แผนย้ายฐาน TruckScale ขึ้นคลาวด์

## ข้อจำกัดที่ตั้งไว้

- แก้ source code หรือ config ของ TruckScale **ไม่ได้**
- เลิกใช้ TruckScale **ไม่ได้** — ยังมี client หลายเครื่องใช้งานอยู่
- client ทุกเครื่องต่อเข้า **MySQL ตัวกลางตัวเดียว** ที่เราเข้าถึงได้
- ปลายทางที่ต้องการคือคลาวด์ (Railway) เพื่อให้ WINSpeed และ App ทำงานร่วมได้สะดวก

## สิ่งที่ตรวจแล้ว

| เรื่อง | ผล |
|---|---|
| Railway เป็น replica ได้ไหม | **ได้** — มี `REPLICATION_SLAVE_ADMIN`, `SUPER`, `SYSTEM_VARIABLES_ADMIN` · `gtid_mode=ON` · `binlog_format=ROW` · ยังไม่ผูกกับ source ใด |
| กลไก replication | ทดสอบครบบน localhost — ตามหลัง 0 วินาที · เขียนสดถึงปลายทางใน ~0.7 วินาที |
| รุ่น MySQL | Railway 9.7.1 · ชุดทดสอบใช้ 9.7.2 |
| `server_id` ของ Railway | **1** — ต้องตั้ง source ให้เป็นเลขอื่น ไม่งั้นชนกัน |

## 🔴 ตัวติดที่ต้องแก้ก่อน ไม่ใช่เรื่องเครือข่าย

**App เขียนลงฐาน TruckScale เหมือนกับเครื่องชั่ง** ไม่ได้อ่านอย่างเดียว

`services/truckscale-db.js` เขียนจริงห้าจุด — `INSERT INTO tbl_keyone` (คิวก่อนชั่ง) ·
`DELETE FROM tbl_keyone` (ยกเลิก) · `INSERT INTO tblproduct_detail` ·
`UPDATE tblscale` · `INSERT INTO tblscale` (write-back ตอนส่งของ)

replica ที่มีคนเขียนลงไปด้วยจะพังทันที — คีย์ซ้ำบ้าง GTID ขัดกันบ้าง
และของที่เขียนลงปลายทางจะถูกทับเมื่อ source ส่งข้อมูลชุดเดียวกันมา

**หลักฐานว่าเรื่องนี้เกิดขึ้นแล้ว:** แถวใหม่สุดของ `tbl_keyone` บน Railway คือ
`PHASEC-01` (25/08/2569) ซึ่ง**เป็นแถวที่ App เขียนตอนทดสอบ** ไม่ใช่ของเครื่องชั่ง

ซ้ำร้าย `TS_PRODUCTION_HOSTS` ใน `.env` **ว่างเปล่า** ตัวกันเขียนฐานจริงจึงไม่เคยทำงานเลย
(ดู `assertWritableTarget()`) — ต้องตั้งค่านี้ทุกสภาพแวดล้อม

## สถาปัตยกรรมเป้าหมาย

```
โรงงาน (LAN)                          คลาวด์
┌────────────────────────┐            ┌─────────────────────┐
│ TruckScale clients ─┐  │            │ Railway MySQL       │
│                     ▼  │  binlog    │ (replica อ่านอย่างเดียว)│
│   MySQL ตัวกลาง ───────┼───────────▶│                     │
│   (แหล่งความจริง)      │  ผ่านอุโมงค์  │  ใช้ทำรายงาน/สำรอง    │
└────────────▲───────────┘            └─────────────────────┘
             │ เขียน (ผ่านอุโมงค์เดียวกัน)
        App / WINSpeed
```

**MySQL ที่โรงงานยังเป็นแหล่งความจริงเพียงที่เดียว** ทั้งเครื่องชั่งและ App เขียนที่นั่น
Railway รับข้อมูลทางเดียวไว้อ่าน

### ทำไมไม่ย้ายทั้งก้อนขึ้นคลาวด์

ถ้าเครื่องชั่งต้องวิ่งผ่านอินเทอร์เน็ตทุกครั้งที่ชั่ง เน็ตล่มเมื่อไรชั่งไม่ได้ทั้งโรงงาน
และเราแก้ config ฝั่ง client ไม่ได้อยู่แล้ว การคงฐานไว้ที่โรงงานจึงไม่ใช่การประนีประนอม
แต่เป็นข้อกำหนดจากความพร้อมใช้งาน

*(ทางเลือกที่เคยคิด: วาง proxy ที่โฮสต์เดิมแล้ว forward ขึ้นคลาวด์ — client ไม่ต้องแก้จริง
แต่ทุกการชั่งจะขึ้นกับลิงก์อินเทอร์เน็ต ไม่แนะนำ)*

### ทำไม App ต้องอ่านจาก source ไม่ใช่ replica

App เขียนคิวก่อนชั่งแล้ว**อ่านกลับทันที** (ค้นตั๋วที่เปิดอยู่ด้วย movebill หรือทะเบียน)
ถ้าอ่านจาก replica ที่ตามหลังอยู่ จะหาแถวที่เพิ่งเขียนไม่เจอ แล้วไปสร้างซ้ำ
Railway จึงมีไว้ทำรายงานและสำรอง ไม่ใช่ทางอ่านหลักของ App

## ขั้นตอน

| # | งาน | สถานะ |
|---|---|---|
| 1 | ตั้ง `TS_PRODUCTION_HOSTS` ให้ตัวกันเขียนทำงาน · dev ชี้ไปฐาน Docker | ทำแล้ว |
| 2 | ล้างแถวที่ App เขียนลง Railway ตอนทดสอบ | รอเจ้าของสั่ง |
| 3 | เปิด binlog + GTID + ตั้ง `server_id` ที่ MySQL โรงงาน · สร้างบัญชี `repl` | **ต้องรีสตาร์ต MySQL = เครื่องชั่งหยุดชั่วคราว** |
| 4 | เปิดอุโมงค์ขาออกจากโรงงาน (Cloudflare Tunnel / autossh / Tailscale) | รอเลือกเครื่องมือ |
| 5 | ดัมป์ฐานตั้งต้นจากโรงงานขึ้น Railway พร้อม GTID แล้วต่อสาย | สคริปต์พร้อม |
| 6 | ย้าย `MYSQL_HOST` ของ App ให้ชี้ source ผ่านอุโมงค์ | รอข้อ 4 |
| 7 | เฝ้า lag + ตั้งการแจ้งเตือนเมื่อสายหลุด | ยังไม่ทำ |

ขั้นที่ 3 คือขั้นเดียวที่มีผลกระทบกับผู้ใช้จริง — ต้องนัดเวลา

## ที่ยังพิสูจน์ไม่ได้จากเครื่องนี้

- **อุโมงค์** — ต้องมีเครื่องที่โรงงานและบัญชีผู้ให้บริการ
- **replication ข้ามอินเทอร์เน็ตจริง** — ติดที่ NAT เหมือนกัน ทดสอบได้เมื่อมีอุโมงค์แล้ว
- **binlog ที่ MySQL โรงงาน** — ยังไม่รู้ว่าเปิดอยู่หรือไม่ ต้องเข้าไปดูที่เครื่องจริง

กลไกฝั่งที่ควบคุมได้ทดสอบผ่านหมดแล้ว เหลือเฉพาะส่วนที่ต้องใช้ของจริง
