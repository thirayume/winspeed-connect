# แผนย้ายฐาน TruckScale ขึ้นคลาวด์

## ข้อจำกัดที่ตั้งไว้

- แก้ source code หรือ config ของ TruckScale **ไม่ได้**
- เลิกใช้ TruckScale **ไม่ได้** — ยังมี client หลายเครื่องใช้งานอยู่
- client ทุกเครื่องต่อเข้า **MySQL ตัวกลางตัวเดียว** ที่เราเข้าถึงได้
- ปลายทางที่ต้องการคือคลาวด์ (Railway) เพื่อให้ WINSpeed และ App ทำงานร่วมได้สะดวก

## ✅ ย้าย 100% ขึ้นคลาวด์ได้ โดยไม่แตะตัวโปรแกรมเลย — พิสูจน์แล้ว 31/08/2569

นี่คือทางที่เจ้าของบอกว่าต้องการมากที่สุด และตอนนี้ยืนยันแล้วว่าทำได้

### หลักฐาน

แกะไบนารีในโฟลเดอร์ TruckScale ทั้งชุด (`WorldFerth.exe`, `libDatabases.dll`, `PrintReport.dll`)

| สิ่งที่ตรวจ | ผล |
|---|---|
| connection string ที่ฝังไว้ | มีสองเส้นเท่านั้น — `DSN=TruckScales;UID=<ผู้ใช้>;PWD=<รหัส>` และ `DSN=TruckScaleV5_Backup;...` (ค่าจริงไม่เขียนไว้ใน repo สาธารณะนี้ · `Set-TruckScaleDSN.ps1` อ่านจาก exe ให้เอง) |
| IP หรือชื่อโฮสต์ในไบนารี | **ไม่มีเลยแม้แต่ตัวเดียว** (ค้นทั้ง ASCII และ UTF-16) |
| API ที่ใช้ต่อฐาน | `System.Data.Odbc` อย่างเดียว ไม่มี MySQL connector ตัวอื่น |
| สถาปัตยกรรม | x86 ทุกไฟล์ · .NET CLR v2.0.50727 |

**ปลายทางฐานข้อมูลถูกกำหนดโดย ODBC DSN ของ Windows ล้วน ๆ**

ทดสอบจริง: สร้าง DSN ชื่อ `TruckScales` ชี้ MySQL ใน Docker (คนละเครื่อง คนละพอร์ต)
แล้วเปิดการเชื่อมต่อด้วยสตริงเดียวกับที่ฝังอยู่ในโปรแกรมทุกตัวอักษร → **ต่อติด อ่านข้อมูลได้**

### ทำไมไม่ขัดกับข้อจำกัด "แก้ config ของ TruckScale ไม่ได้"

DSN ไม่ใช่ config ของ TruckScale แต่เป็นค่าของ **Windows** อยู่ในรีจิสทรี
ไฟล์ในโฟลเดอร์ TruckScale ไม่ถูกแตะแม้แต่ไฟล์เดียว ตัวโปรแกรมไม่รู้ด้วยซ้ำว่ามีอะไรเปลี่ยน

### เครื่องมือ

- `Set-TruckScaleDSN.ps1` — ย้าย DSN ของเครื่องลูกข่ายไปฐานใหม่
  สำรองค่าเดิมแบบประทับเวลาทุกครั้ง · `-Restore` ถอยกลับสภาพก่อนแตะเครื่องครั้งแรก ·
  `-TestOnly` ตรวจอย่างเดียว · คงไดรเวอร์และ CHARSET เดิมของเครื่องไว้
  ทดสอบวงจรเต็มแล้ว: เครื่องเปล่า → ตั้งค่า → ย้ายซ้ำไปอีกฐาน → ถอยกลับสภาพเดิม
- `Harden-CloudMySQL.sql` — เตรียมบัญชีที่ปลายทาง

### 🔴 ราคาที่ต้องจ่าย: บัญชีและรหัสผ่านที่ฝังอยู่ในโปรแกรม

ทดสอบยืนยันแล้วว่า **UID/PWD ในสตริงของโปรแกรมทับค่าที่ตั้งใน DSN**
(ตั้งรหัสแข็งไว้ใน DSN แล้วให้โปรแกรมส่งรหัสที่ฝังไว้มา → ถูกปฏิเสธ)
ฐานปลายทางจึงต้องมีบัญชีชื่อและรหัสตรงกับที่ฝังไว้จริง ๆ เลี่ยงไม่ได้
**รหัสนั้นสั้นและเดาง่ายมาก** — นี่คือแกนของความเสี่ยงทั้งหมดในทางเลือกนี้

ทำให้ปลอดภัยพอรับได้ด้วยการทำให้บัญชีนั้น "ชื่อ root แต่ไม่ใช่ root" — ทดสอบผ่านแล้ว:

| มาตรการ | ผลที่ทดสอบได้ |
|---|---|
| ให้สิทธิ์แค่ `SELECT/INSERT/UPDATE/DELETE` บน `db_truckscale` เท่านั้น | โปรแกรมอ่านเขียนได้ปกติ · `DROP DATABASE` ถูกบล็อก |
| `REQUIRE SSL` | ต่อผ่าน TLS 1.3 (`TLS_AES_128_GCM_SHA256`) |
| จำกัด host เป็น IP โรงงาน + ปิดพอร์ตที่ไฟร์วอลล์ | ด่านหลัก กันตั้งแต่ก่อนถึงชั้นตรวจรหัส |

**ข้อสรุปเรื่องผู้ให้บริการ:** Railway ไม่มีไฟร์วอลล์ระดับ IP — พอร์ตเปิดสาธารณะโดยมีแค่
รหัสสั้น ๆ นั้นกั้น ซึ่งรับไม่ได้
**ถ้าเลือกทางนี้ ฐาน TruckScale ต้องอยู่บน VPS ที่ตั้ง ufw ได้ ไม่ใช่ Railway**

### สิ่งที่ยังต้องยืนยันหน้างาน

1. **รันตัวโปรแกรมจริงกับฐานใหม่** — เครื่องนี้รัน `WorldFerth.exe` ไม่ได้
   (`BadImageFormatException` เพราะไม่มี .NET 3.5 และ Crystal Reports runtime)
   ต้องทดสอบบนเครื่องที่มี TruckScale อยู่แล้ว หนึ่งเครื่อง นอกเวลาทำการ
2. **เน็ตโรงงานล่มแล้วเกิดอะไรขึ้น** — ย้ายขึ้นคลาวด์แล้ว เน็ตล่ม = ชั่งไม่ได้ทั้งโรงงาน
   นี่คือความเสี่ยงที่แลกมากับความสะดวก ต้องให้เจ้าของตัดสินโดยรู้ตัว
3. **จำนวนเครื่องลูกข่ายทั้งหมด** — ต้องรัน `Set-TruckScaleDSN.ps1` ทุกเครื่อง ห้ามตกเครื่องใด
   เครื่องที่ตกจะยังเขียนลงฐานเก่า แล้วข้อมูลแยกร่างทันที

## สิ่งที่ตรวจแล้ว

| เรื่อง | ผล |
|---|---|
| Railway เป็น replica ได้ไหม | **ได้** — มี `REPLICATION_SLAVE_ADMIN`, `SUPER`, `SYSTEM_VARIABLES_ADMIN` · `gtid_mode=ON` · `binlog_format=ROW` · ยังไม่ผูกกับ source ใด |
| กลไก replication | ทดสอบครบบน localhost — ตามหลัง 0 วินาที · เขียนสดถึงปลายทางใน ~0.7 วินาที |
| รุ่น MySQL | Railway 9.7.1 · ชุดทดสอบใช้ 9.7.2 |
| `server_id` ของ Railway | **1** — ต้องตั้ง source ให้เป็นเลขอื่น ไม่งั้นชนกัน |

## 🔴 ตัวติดที่ต้องแก้ก่อน ไม่ใช่เรื่องเครือข่าย

**App เขียนลงฐาน TruckScale เหมือนกับเครื่องชั่ง** ไม่ได้อ่านอย่างเดียว

`services/truckscale-db.js` เขียนจริงห้าจุด — `INSERT INTO tbl_keyone` (คิวก่อนชั่ง) ·
`DELETE FROM tbl_keyone` (ยกเลิก) · `INSERT INTO tblproduct_detail` ·
`UPDATE tblscale` · `INSERT INTO tblscale` (write-back ตอนส่งของ)

replica ที่มีคนเขียนลงไปด้วยจะพังทันที — คีย์ซ้ำบ้าง GTID ขัดกันบ้าง
และของที่เขียนลงปลายทางจะถูกทับเมื่อ source ส่งข้อมูลชุดเดียวกันมา

**หลักฐานว่าเรื่องนี้เกิดขึ้นแล้ว:** แถวใหม่สุดของ `tbl_keyone` บน Railway คือ
`PHASEC-01` (25/08/2569) ซึ่ง**เป็นแถวที่ App เขียนตอนทดสอบ** ไม่ใช่ของเครื่องชั่ง

ซ้ำร้าย `TS_PRODUCTION_HOSTS` ใน `.env` **ว่างเปล่า** ตัวกันเขียนฐานจริงจึงไม่เคยทำงานเลย
(ดู `assertWritableTarget()`) — ต้องตั้งค่านี้ทุกสภาพแวดล้อม

## สถาปัตยกรรมเป้าหมาย

```
โรงงาน (LAN)                          คลาวด์
┌────────────────────────┐            ┌─────────────────────┐
│ TruckScale clients ─┐  │            │ Railway MySQL       │
│                     ▼  │  binlog    │ (replica อ่านอย่างเดียว)│
│   MySQL ตัวกลาง ───────┼───────────▶│                     │
│   (แหล่งความจริง)      │  ผ่านอุโมงค์  │  ใช้ทำรายงาน/สำรอง    │
└────────────▲───────────┘            └─────────────────────┘
             │ เขียน (ผ่านอุโมงค์เดียวกัน)
        App / WINSpeed
```

**MySQL ที่โรงงานยังเป็นแหล่งความจริงเพียงที่เดียว** ทั้งเครื่องชั่งและ App เขียนที่นั่น
Railway รับข้อมูลทางเดียวไว้อ่าน

### ทำไมไม่ย้ายทั้งก้อนขึ้นคลาวด์

> แก้ 31/08/2569 — เหตุผลข้อ "แก้ฝั่ง client ไม่ได้" **ตกไปแล้ว** เพราะพิสูจน์ได้ว่า
> เปลี่ยน ODBC DSN อย่างเดียวก็ย้ายฐานได้ (ดูหัวข้อบนสุด)
> เหลือเหตุผลเดียวคือความพร้อมใช้งาน ซึ่งยังหนักอยู่

ถ้าเครื่องชั่งต้องวิ่งผ่านอินเทอร์เน็ตทุกครั้งที่ชั่ง เน็ตล่มเมื่อไรชั่งไม่ได้ทั้งโรงงาน
การชั่งเป็นงานที่หยุดไม่ได้ รถเข้าคิวรออยู่หน้าโรงงาน
**นี่คือข้อเดียวที่ยังกันไม่ให้เลือกทาง ก. และเป็นเรื่องที่เจ้าของต้องตัดสิน ไม่ใช่เรื่องเทคนิค**

*(ทางเลือกที่เคยคิด: วาง proxy ที่โฮสต์เดิมแล้ว forward ขึ้นคลาวด์ — ตอนนี้ไม่จำเป็นแล้ว
เพราะแก้ DSN ตรง ๆ ได้ และ proxy ก็ไม่ได้แก้ปัญหาเน็ตล่มอยู่ดี)*

### ทำไม App ต้องอ่านจาก source ไม่ใช่ replica

App เขียนคิวก่อนชั่งแล้ว**อ่านกลับทันที** (ค้นตั๋วที่เปิดอยู่ด้วย movebill หรือทะเบียน)
ถ้าอ่านจาก replica ที่ตามหลังอยู่ จะหาแถวที่เพิ่งเขียนไม่เจอ แล้วไปสร้างซ้ำ
Railway จึงมีไว้ทำรายงานและสำรอง ไม่ใช่ทางอ่านหลักของ App

## เปลี่ยนวิธี — ไม่ใช้ replication ของ MySQL แล้ว

ข้อจำกัดสองข้อที่เพิ่มมาทีหลังตัดทางเลือกเดิมทิ้ง:

1. **ไม่มีอุโมงค์ และไม่อยากใช้** — โรงงานต่อ**ออก**ได้อย่างเดียว
   แต่ replication ของ MySQL ให้ปลายทางเป็นฝ่ายต่อ**เข้า**หาต้นทาง จึงต้องมีอุโมงค์เสมอ
2. **ห้ามกระทบขั้นที่ต้องรีสตาร์ต MySQL โรงงาน** — เปิด binlog ต้องรีสตาร์ต = เครื่องชั่งหยุดทุกเครื่อง

จึงเปลี่ยนไปใช้ **ตัวผลักแบบ watermark** ที่รันในโรงงาน → `push-agent/`

| | replication | ตัวผลัก |
|---|---|---|
| ทิศทางการต่อ | ปลายทางต่อเข้าโรงงาน (ต้องมีอุโมงค์) | โรงงานต่อออก |
| แก้ config / รีสตาร์ต MySQL โรงงาน | ต้อง | **ไม่ต้อง** |
| สิทธิ์ที่ต้นทาง | `REPLICATION SLAVE` | `SELECT` |
| ความหน่วง | ~วินาที | ตามรอบ (ปริยาย 60 วินาที) |

ชุด replication ใน `docker-compose.yml` **ยังเก็บไว้** เผื่อวันหนึ่งมีอุโมงค์แล้วอยากได้ความหน่วงต่ำ
กลไกทดสอบผ่านแล้วทั้งคู่ เลือกใช้ได้ตามสถานการณ์

### ทดสอบตัวผลักกับ Railway จริงแล้ว (31/08/2569)

ต้นทาง MySQL ใน Docker · ปลายทาง Railway (ฐานทดสอบแยก ลบทิ้งแล้ว)
โหลดครั้งแรกครบทุกตาราง · เพิ่มแถวใหม่ตามทัน · **แก้น้ำหนักตั๋วเดิมย้อนหลังก็ตามทัน**
(`weight_net` 10000 → 11000) ซึ่งเป็นจุดที่ watermark เปล่า ๆ จะพลาด

### ข้อ 6 ยังต้องตัดสิน

App เขียนลงฐาน TruckScale จริง (5 จุด) ถ้าคลาวด์เป็นสำเนาทางเดียว
ของที่ App เขียนลงคลาวด์จะถูกตัวผลักทับเมื่อส่งรอบถัดไป

ทางเลือก:
- **ก.** App เขียนลง MySQL โรงงาน (ต้องเข้าถึงได้จากที่ App รัน) — ข้อมูลมีที่เดียว ถูกต้องที่สุด
- **ข.** App เขียนลงคลาวด์ แล้วให้ตัวผลักข้ามช่วง `one_id` ที่ App เป็นคนออก — ซับซ้อนและเปราะ
- **ค.** App หยุดเขียน TruckScale ใช้ทางอื่นแทน — กระทบฟีเจอร์ที่มีอยู่

แนะนำ **ก.** ถ้า App เข้าถึง MySQL โรงงานได้

## ที่ยังพิสูจน์ไม่ได้จากเครื่องนี้

- **ที่อยู่ MySQL โรงงาน** — ยืนยันแล้วว่า**ไม่ได้ฝังในตัวโปรแกรม** อยู่ใน ODBC DSN ของแต่ละ client
  รันบนเครื่องที่มี TruckScale (ดู User DSN ด้วย เผื่อไม่ได้ตั้งแบบ System):
  ```powershell
  foreach ($r in 'HKLM:\SOFTWARE\WOW6432Node\ODBC\ODBC.INI','HKCU:\SOFTWARE\ODBC\ODBC.INI') {
    foreach ($d in 'TruckScales','TruckScaleV5_Backup') {
      $k = Join-Path $r $d
      if (Test-Path $k) { "$k"; Get-ItemProperty $k | Select-Object SERVER,PORT,DATABASE,Driver,CHARSET }
    }
  }
  ```
  หรือใช้ `.\Set-TruckScaleDSN.ps1 -TestOnly` ซึ่งอ่านค่าให้พร้อมทดสอบการเชื่อมต่อในตัว
- **ความเร็วจริงจากโรงงาน** — ขึ้นกับลิงก์ที่นั่น ทดสอบได้เมื่อวางตัวผลักแล้ว
- **จำนวนตั๋วที่เปิดค้างพร้อมกัน** — ใช้ตั้ง `REFRESH_TAIL` ให้พอดี ค่าปริยาย 2000 น่าจะเหลือเฟือ

กลไกทั้งหมดทดสอบผ่านกับ Railway จริงแล้ว เหลือเฉพาะตัวเลขที่ต้องวัดหน้างาน
