# กฎการทำงานร่วมกับข้อมูลหลักของ WinSpeed

ฉบับ 18 พ.ย. 2569 (เจ้าของสั่ง: ตารางใดที่ Sale-App ต้องทำงานร่วม ให้ทำ CRUD ได้ครบ พร้อมสำหรับการพัฒนาระยะยาว และไม่เกิดข้อมูลซ้ำซ้อน)

## 1. หลักการ

1. **WinSpeed เป็นต้นฉบับเดียว** ของสินค้า กลุ่มสินค้า ของแถม ลูกค้า และราคา Sale-App ไม่เก็บสำเนาข้อมูลหลักเหล่านี้
   - เก็บได้เฉพาะข้อมูลที่ WinSpeed ไม่มี โดยอ้างอิงด้วยรหัส เช่น `wf.GoodExtra` (กระสอบ/ตัน, กก./กระสอบ, รูปภาพ) ซึ่งใช้ `GoodID` เป็นคีย์
   - ข้อความที่เก็บไว้ในเอกสารหรือประวัติ (เช่น ชื่อสินค้าในบรรทัดบิล ในงบของแถม หรือในประวัติการเบิก) เป็นภาพ ณ เวลานั้น ห้ามย้อนแก้
2. **Sale-App สร้าง แก้ไข และลบข้อมูลหลักของ WinSpeed ที่ทำงานร่วมกันได้** (สินค้า `dbo.EMGood` และหน่วยของสินค้า `dbo.EMGoodMultiUnit`, กลุ่มสินค้า `dbo.EMGoodGroup`, ของแถมคือสินค้ากลุ่ม 1005, ลูกค้า และราคาตามที่มีอยู่เดิม)
   - **ต้องเขียนผ่าน stored procedure ใน schema `wf` เท่านั้น** ห้าม route หรือ service เขียน `INSERT/UPDATE/DELETE` ลง `dbo` เอง
   - ผู้ใช้ฐานข้อมูลของแอปมีสิทธิ์ `EXECUTE` บน `wf` เท่านั้น ไม่มีสิทธิ์เขียน `dbo` โดยตรง
3. **ไม่เปลี่ยนโครงสร้างตารางของ WinSpeed** (ไม่ ALTER/CREATE ใน `dbo`) และ **ไม่ปิด trigger ของ WinSpeed**
   - trigger ตรวจความถูกต้อง (`tI_/tU_/tD_…`) ต้องทำงานทุกครั้ง: ตอนเพิ่ม ตรวจว่าข้อมูลอ้างอิงมีจริง ตอนลบ ห้ามลบถ้ายังมีเอกสารใช้อยู่

## 2. วิธีเขียนข้อมูลหลัก (procedure)

| เรื่อง | กฎ |
|---|---|
| Transaction | procedure ต้องอยู่ใน transaction ของผู้เรียก (`@@TRANCOUNT ≥ 1`) และข้อมูลส่วน Sale-App (`wf.GoodExtra`) บันทึกใน transaction เดียวกัน |
| เลขรหัส | `GoodID` และ `GoodGroupID` ไม่ใช่ identity ให้ใช้ค่าสูงสุด + 1 โดยล็อก `UPDLOCK, HOLDLOCK` ใน transaction เดียวกับการเพิ่ม |
| ค่าตั้งต้น | สินค้าใหม่คัดลอกทุกคอลัมน์ของ WinSpeed จาก **สินค้าต้นแบบในกลุ่มเดียวกัน** (ประเภท ภาษี บัญชี การตั้งค่าคลัง) แล้วตั้งรหัส ชื่อ กลุ่ม และหน่วยของตัวเอง ยอดคงเหลือและต้นทุนเริ่มที่ศูนย์ และเพิ่มแถวหน่วยหลักใน `EMGoodMultiUnit` (สินค้าทุกตัวมีแถวนี้) |
| ห้ามซ้ำ | รหัสสินค้าไม่ซ้ำ, รหัสและชื่อกลุ่มไม่ซ้ำ, ชื่อสินค้าที่ยังขายอยู่ไม่ซ้ำในกลุ่มเดียวกัน |
| การลบ | ลบได้เฉพาะรายการที่ไม่มีอะไรใช้: ไม่มีเอกสาร WinSpeed (trigger ตรวจราว 80 ตาราง) และไม่มีตารางใน Sale-App อ้างถึง ถ้ามีการใช้แล้ว ให้ **งดจำหน่าย** แทนการลบ |
| ประวัติ | ทุกการเปลี่ยนแปลงบันทึก `wf.ChangeEvent` (ผู้ทำจริงและผู้ที่ทำแทน) |
| SQL Server | ต้องรันได้บน SQL Server 2008 R2 ระดับความเข้ากันได้ 80: ห้ามใช้ `THROW`, `TRY_CAST`, `CONCAT`, `IIF`, `CREATE OR ALTER` |
| สิทธิ์ | เพิ่ม แก้ ลบ ข้อมูลหลัก: `ADMIN`, `C_LEVEL` · อ่าน: ทุกบทบาท |

procedure ปัจจุบัน (migration 146 และ 248): `wf.sp_MasterUpdateCustomer`, `wf.sp_MasterSetCustomerInactive`, `wf.sp_MasterUpdatePrice`, `wf.sp_MasterCreatePrice`, `wf.sp_MasterUpdateGoodName`, `wf.sp_MasterSaveGoodGroup`, `wf.sp_MasterDeleteGoodGroup`, `wf.sp_MasterCreateGood`, `wf.sp_MasterUpdateGood`, `wf.sp_MasterSetGoodStatus`, `wf.sp_MasterDeleteGood`

## 3. Migration ที่แก้ข้อมูล

1. จับคู่แบบตรงตัวเท่านั้น (ชื่อหรือรหัสตรงกันทุกตัวอักษร และหนึ่งต่อหนึ่ง) ห้ามใช้ `LIKE '%…%'` หรือจับคู่บางส่วน
2. ห้ามย้อนแก้ประวัติ (การเบิก ใบเสร็จ เอกสาร) ถ้าต้องให้ประวัติเดิมนับรวมกับข้อมูลใหม่ ให้ใช้ตารางจับคู่ (alias) แทนการแก้แถวเดิม
3. บันทึกทุกแถวที่เปลี่ยนในตาราง log เพื่อให้ rollback ย้อนได้ตรงทุกแถว และรันซ้ำได้โดยไม่เปลี่ยนอะไรเพิ่ม
4. ซ้อมใน transaction แล้ว rollback ก่อนทุกครั้ง และรายงานจำนวนที่จับคู่ได้และไม่ได้
5. migration ที่รันไปแล้วห้ามแก้ไฟล์ (ระบบตรวจ checksum) ถ้าผิด ให้ใส่ใน `migration-policy.json` `excludedFiles` แล้วเขียน migration ใหม่ที่ถูก (ตัวอย่าง: 246 ถูกแทนด้วย 249)

## 4. ของแถม (สินค้ากลุ่ม 1005)

- ของแถมทุกรายการคือสินค้า WinSpeed กลุ่ม 1005 (ส่งเสริมการขาย) เพิ่มของแถมใหม่จากหน้าของแถม ระบบตั้งรหัส `PMnnnnn` ต่อจากรหัสล่าสุดให้
- ของแถมรุ่นเก่าที่ไม่มีกลุ่ม (28xxx) ซึ่งมีชื่อตรงกับของแถมกลุ่ม 1005 บันทึกคู่ไว้ใน `wf.GiveawayGoodAlias` (migration 249)
  - งบของแถมชี้ไปที่สินค้ากลุ่ม 1005
  - ประวัติการเบิกของรุ่นเก่ายังนับรวมในงบของรุ่นใหม่ผ่านตารางคู่นี้
  - หน้าเลือกของแถมแสดงเฉพาะรุ่นกลุ่ม 1005 รายการเดียว
- การปิดใช้ของแถมรุ่นเก่าใน WinSpeed (งดจำหน่าย) เป็นการตัดสินใจของเจ้าของ ทำได้จากหน้าสินค้า
