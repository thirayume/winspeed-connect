# โมดูลชั่งของ WINSpeed — `WGHD` / `WGDT` / `WGDTReport`

เจ้าของระบบชี้ว่ามีตารางเหล่านี้ใน WINSpeed ซึ่งรับข้อมูลมาจาก TruckScale
และเสนอว่า **น่าจะใช้แทนฐาน TruckScale ได้**

ตรวจกับข้อมูลจริงบน Azure เมื่อ 31/08/2569 แล้ว — คำตอบสั้น ๆ คือ **ยังแทนไม่ได้**
แต่สิ่งที่เจอมีน้ำหนักต่อแผนระยะยาวมาก และมีเรื่องที่ต้องแจ้งโรงงานทันทีหนึ่งเรื่อง

## โครงสร้าง — ออกแบบมาถูกทาง

| ตาราง | บทบาท | เทียบกับ MySQL |
|---|---|---|
| `WGHD` (31 คอลัมน์) | หัวรายการชั่ง — ทะเบียนรถ ลูกค้า `DocuNo` `MoveBill` น้ำหนักเข้า/ออก/สุทธิ สถานะคิว | `tblscale` |
| `WGDT` (27 คอลัมน์) | บรรทัดสินค้า — `GoodID` กระสอบ ตัน `STOCode` **`CouponNo`** | `tblproduct_detail` |
| `WGDTReport` (20 คอลัมน์) | มุมมองแบนสำหรับออกรายงาน | — |

ครบทุกช่องที่จำเป็น รวม `CouponNo` ซึ่ง TruckScale ไม่มี — **ปลายทางที่ควรไปคือตรงนี้**

## ❌ ทำไมยังแทนไม่ได้ตอนนี้

| ตรวจ | ผล |
|---|---|
| จำนวนแถว | `WGHD` **181** · `WGDT` 311 · `WGDTReport` 29 — เทียบกับ MySQL `tblscale` **408,501** |
| ช่วงเวลา | **8 พ.ค. – 25 มิ.ย. 2569 เท่านั้น** ไม่มีประวัติก่อนหน้าเลย |
| น้ำหนักเข้า | 21 / 181 |
| น้ำหนักออก | 15 / 181 |
| **น้ำหนักสุทธิ** | **5 / 181** |
| **`CouponNo`** | **0 / 311 — ว่างทั้งหมด** |
| `RefNo` | 0 / 311 |

ไม่มีประวัติ · น้ำหนักแทบไม่มี · เลขตั๋วไม่มีเลย — ใช้เป็นแหล่งข้อมูลแทนไม่ได้

## 🔴 เรื่องที่ต้องแจ้งโรงงาน: ตัวป้อนน้ำหนักหยุดตั้งแต่ 28 พ.ค.

ดูรายวันตามวันลงทะเบียน:

| ช่วง | ลงทะเบียน | มีน้ำหนัก |
|---|---|---|
| 8–28 พ.ค. 2569 | 132 | 15 |
| **5–25 มิ.ย. 2569** | **49** | **0** |

หลัง 28 พ.ค. **ไม่มีแถวไหนได้น้ำหนักเลยสักแถว** แต่คนยังลงทะเบียนรถเข้ามาเรื่อย ๆ ถึง 25 มิ.ย.
แปลว่าคนหน้างานยังใช้หน้าจอนี้อยู่ แต่ข้อมูลที่ควรไหลกลับมาจากตาชั่งไม่ไหลแล้ว
และดูเหมือนยังไม่มีใครสังเกต

`UpdateBy` เป็น `NULL` ทั้ง 181 แถว — เขียนโดยกระบวนการอัตโนมัติ ไม่ใช่คนกรอก

## ✅ สิ่งที่ได้จากการตรวจครั้งนี้ และมีค่ามาก

### 1. `EMSTOType` คือ taxonomy คลังเดียวกับที่รายงานเก่าใช้

`WGDT.STOCode` อ้าง `dbo.EMSTOType` ซึ่งให้ค่าตรงกับ `pd_pro_Godown` ใน MySQL **ทุกตัว**:

| `STOCode` | `EMSTOType` | `pd_pro_Godown` ใน MySQL |
|---|---|---|
| `สB` | สายพาน(B/B) | `สายพาน(B/B)` |
| `สH` | สายพาน(H/P) | `สายพาน(H/P)` |
| `คB` | คลัง(B/B) | `คลัง(B/B)` |
| `คH` | คลัง(H/P) | `คลัง(H/P)` |
| `03` `04` | โกดัง3 · โกดัง4 | `โกดัง3` · `โกดัง4` |

**ยืนยันข้อสรุปเรื่องรายงานจากแหล่งที่สองโดยอิสระ** — ตัวแยกว่าใบไหนเป็น `RptSaYPan`
หรือ `RptKlungSinKa` คือคลัง และ WINSpeed รู้จักคลังชุดเดียวกันนี้อยู่แล้วในชื่อ `EMSTOType`
ดู [TRUCKSCALE-REPORT-PLAN](TRUCKSCALE-REPORT-PLAN.md)

แปลว่ารายงานใบจ่ายสินค้า **ดึงคลังจาก WINSpeed ได้ ไม่ต้องพึ่ง MySQL**

### 2. ผูกกับใบสั่งขายจริง

`WGHD.DocuNo` ตรงกับ `SOHD` — เจอเป็นใบสั่งจอง (103) 124 ครั้ง และใบส่งขาย (104) 111 ครั้ง
(ตัวเลขรวมเกิน 181 เพราะ `DocuNo` ไม่ unique ข้าม `DocuType` ใบเดียวจึงตรงได้ทั้งสองชนิด
ตามสายเล่ม 103→104 ที่ยืนยันไว้แล้ว)

เป็นการจับคู่รถ↔ใบสั่งขายแบบเดียวกับที่ App ทำอยู่ แต่ทำในตัว WINSpeed เอง

## ข้อเสนอ

**ระยะสั้น — ไม่เปลี่ยนแหล่งข้อมูล** เดินหน้าย้าย TruckScale ไป Hostinger ตาม
[CUTOVER-to-hostinger](../../../deploy/truckscale-replica/CUTOVER-to-hostinger.md)
เพราะ `WGHD` ยังไม่มีข้อมูลพอจะพึ่งได้ และการย้ายฐานถอยกลับได้

**ระยะยาว — ปลายทางควรเป็น `WGHD`/`WGDT` ไม่ใช่ TruckScale บนคลาวด์**
โมดูลนี้อยู่ใน WINSpeed อยู่แล้ว มี `CouponNo` ในตัว ผูกกับ `SOHD` ตรง ๆ
และใช้ `EMSTOType` ร่วมกับระบบอื่น ถ้าทำให้มันรับน้ำหนักได้จริง จะเลิกใช้ TruckScale ได้ทั้งระบบ
ซึ่งดีกว่าการยกฐาน TruckScale ขึ้นคลาวด์แล้วใช้ต่อไปอีกสิบปี

**คำถามที่ต้องถามโรงงานก่อนตัดสินระยะยาว**

1. ใครเปิดใช้โมดูลนี้เมื่อ พ.ค. และตั้งใจให้มันแทน TruckScale หรือใช้คู่กัน
2. ตัวป้อนน้ำหนักที่หยุดไปเมื่อ 28 พ.ค. เป็นของ Prosoft หรือเขียนเอง
3. ถ้าซ่อมให้ไหลได้ จะยอมย้ายไปใช้เต็มตัวไหม — เพราะถ้ายอม แผนย้ายฐานขึ้นคลาวด์
   จะกลายเป็นงานชั่วคราวที่ไม่ต้องลงแรงมาก
