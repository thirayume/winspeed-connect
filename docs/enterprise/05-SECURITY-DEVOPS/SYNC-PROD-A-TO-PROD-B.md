# ขั้นตอนซิงค์ข้อมูลจาก PROD-A ไป PROD-B

> ## 🛑 PENDING & HOLD — ยังไม่ดำเนินการ (เจ้าของระบบสั่ง 3 ก.ย. 2569)
>
> **อย่าเพิ่งขอ SSH key จากผู้ดูแลเครื่อง Azure และอย่าเพิ่งรันขั้นตอนใด ๆ ในเอกสารนี้**
>
> เหตุผล — เจ้าของระบบกำลังพิจารณาทางที่ต่างออกไป: **ย้ายไป deploy ใน private network
> แล้วเข้าถึงผ่าน VPN** ซึ่งถ้าเลือกทางนั้น ปัญหา "ดึง `.bak` ออกจาก Azure ไม่ได้"
> จะหายไปเองโดยไม่ต้องเปิดพอร์ตหรือแจก SSH key ให้ใครเลย
>
> เอกสารนี้จึงเก็บไว้เป็นทางเลือกที่วิเคราะห์ไว้แล้ว **ไม่ใช่แผนที่ตกลงจะทำ**
> รอการตัดสินใจเรื่องสถาปัตยกรรมเครือข่ายก่อน
>
> **สถานะเนื้อหา: ร่าง — ยังไม่เคยรันจริงแม้แต่ครั้งเดียว**
> ถ้าวันหนึ่งกลับมาใช้ทางนี้ ครั้งแรกต้องซ้อมกับ `dbwins_worldfert9_test` บน Hostinger ก่อน
> ห้ามยิงใส่ PROD-B ตรง ๆ

## 1. ทำไมต้องมีขั้นตอนนี้

| | PROD-A | PROD-B |
|---|---|---|
| ที่อยู่ | Railway + Vercel + **Azure SQL** `20.255.185.14` | Hostinger ทั้งกอง `76.13.190.104` |
| บทบาท | **ใช้งานจริง** — รับใบสั่งขายทุกวัน | **สำรอง** — ยังไม่มีคนใช้ (เจ้าของยืนยัน 03/09/2569) |
| โค้ด | v1.9.0 | v1.9.0 — **ตรงกันแล้ว** |
| ข้อมูล | เดินหน้าต่อเนื่อง | **หยุดนิ่งที่สำเนาวันที่ restore ไว้ (~2 ก.ค. 2569)** |

**ช่องว่างคือข้อมูล ไม่ใช่โค้ด** — B พร้อมในแง่ระบบแล้ว แต่ถ้าต้องสลับไปใช้จริงวันนี้
ใบสั่งขายตั้งแต่ ก.ค. เป็นต้นมาจะหายไปทั้งหมด เอกสารนี้ปิดช่องว่างนั้น

## 2. ข้อจำกัดที่กำหนดรูปแบบของวิธีทั้งหมด

### 2.1 เราไม่มีสิทธิ์เข้าเครื่อง Azure

| ตรวจ (03/09/2569) | ผล |
|---|---|
| Azure พอร์ต 1433 | **เปิด** |
| Azure พอร์ต 22 | **เปิด** — แต่ **ไม่มีคีย์ที่ใช้ได้** (ลอง 6 คู่ user/key ได้ `Permission denied (publickey)` ทุกอัน) |
| Azure พอร์ต 445 (SMB) | ปิด |

> คอมเมนต์ใน `deploy/db-rebuild/rebuild-remote-mssql.js` เขียนว่า *"Azure เข้าได้แค่พอร์ต 1433 ไม่มี SSH"*
> **ผลลัพธ์ตรง แต่เหตุผลไม่ตรง** — พอร์ต 22 เปิดอยู่ ที่เข้าไม่ได้เพราะไม่มีคีย์
> ความต่างนี้สำคัญ เพราะแปลว่า **ติดตั้งคีย์อันเดียวก็ปลดล็อกวิธีที่ง่ายที่สุดได้ทันที**

`BACKUP DATABASE` สั่งผ่าน 1433 ได้ แต่ไฟล์ `.bak` จะไปอยู่บน **ดิสก์ของเครื่อง Azure**
และเราไม่มีทางดึงไฟล์นั้นออกมาผ่าน 1433 อย่างเดียว — นี่คือแก่นของปัญหา

### 2.2 การ RESTORE ทับ จะลบของบน B ทิ้ง

`RESTORE` เอาสถานะทั้งฐานจาก `.bak` มาแทนที่ สิ่งที่หายไปคือ

| หายไป | กู้คืนโดย |
|---|---|
| **schema `wf` ทั้งหมด** (`.bak` ของ WINSpeed ไม่มี `wf`) | `run_migrations.js` สร้างใหม่ |
| **database users** `wf_reader` / `wf_owner` | `finalize-mssql.sh` สร้างใหม่ |
| ผู้ใช้แอปทั้ง 62 คน + ค่าตั้งต้น | `seed_admin.js` + migration seed |

**ทั้งสามอย่างนี้ `restore-mssql.sh` จัดการให้อัตโนมัติแล้ว** (ดู §4)

### 2.3 ⚠ ของที่จะหายจริง ๆ และไม่มีใครกู้ให้

| ตาราง | บน B | บน A | ผลถ้า restore |
|---|---|---|---|
| `wf.WeighInbox` | **271,963** | 220,396 | **B เสีย 51,567 แถว** |
| ตาราง `wf` อื่นทั้งหมด | เท่ากันทุกตาราง | เท่ากัน | ไม่กระทบ |

`WeighInbox` คือข้อมูลที่ดึงมาจาก MySQL ของ TruckScale ซึ่ง **ยกเลิกไปแล้วเมื่อ 03/09/2569**
worker ที่เติมตารางนี้ถูกปิด ข้อมูลจึงไม่เดินต่อทั้งสองฝั่งและไม่มีอะไรอ่านมันแล้ว

**ประเมิน: ยอมให้หายได้** — แต่ต้องเป็นการตัดสินใจ ไม่ใช่ผลข้างเคียงที่เพิ่งมารู้ทีหลัง
ถ้าต้องการเก็บ ให้ `SELECT * INTO` ออกไปไว้ตารางสำรองก่อน restore

### 2.4 ขนาดและพื้นที่

|---|---|

## 3. ทางเลือกสามทาง

| | ทาง ก. SSH + .bak | ทาง ข. BACPAC ผ่าน 1433 | ทาง ค. BACKUP TO URL |
|---|---|---|---|
| ต้องเตรียมอะไร | **ติดตั้ง SSH key บน Azure** (พอร์ต 22 เปิดอยู่แล้ว) | ไม่ต้อง — `SqlPackage.exe` มีในเครื่องแล้ว | Azure Storage account + credential |
| ความเที่ยงตรง | **ครบทุกอย่าง** (สำเนาระดับหน้า) | schema + data เท่านั้น | **ครบทุกอย่าง** |
| ความเสี่ยง | ต่ำ — ใช้สคริปต์ที่มีอยู่แล้วทั้งเส้น | **สูง** — bacpac ของฐาน 3.8 GB / 735 ตาราง ที่มี trigger 1,289 ตัว มักล้มกลางทาง | ปานกลาง — พึ่งบริการภายนอกเพิ่ม |
| เวลาต่อรอบ | สั้น (สคริปต์เดียว) | นาน (หลายชั่วโมง) | ปานกลาง |
| งานตั้งต้น | **ครั้งเดียว** | ไม่มี | ปานกลาง |

### เลือกทาง ก.

เหตุผลหลักคือ **ฝั่ง B ทำเสร็จหมดแล้ว** — `restore-mssql.sh` → `finalize-mssql.sh` เดินลำดับ
logins → users → roles → `run_migrations.js` → grants → `seed_admin.js` ให้ครบถูกต้องอยู่แล้ว
ชิ้นที่ขาดมีชิ้นเดียวคือ **เอา `.bak` ออกจาก Azure ให้ได้** และพอร์ต 22 ก็เปิดรออยู่แล้ว
ติดตั้งคีย์ครั้งเดียว จบเป็นงานคำสั่งเดียวตลอดไป

> ทาง ข. เป็นทางสำรองถ้าเจ้าของเครื่อง Azure ไม่ยอมให้ติดตั้งคีย์
> อย่าเลือกเป็นทางหลัก — bacpac กับฐาน WINSpeed ที่มาจาก SQL 2008 มีโอกาสล้มสูงมาก

## 4. ขั้นตอนทาง ก.

### ขั้นที่ 0 — งานตั้งต้น ทำครั้งเดียว

1. สร้างคู่กุญแจใหม่เฉพาะงานนี้ (อย่าใช้ซ้ำกับคีย์ Hostinger)
   ```bash
   ssh-keygen -t ed25519 -C "worldfert-azure-backup" -f ~/.ssh/worldfert-azure
   ```
2. ให้ผู้ดูแลเครื่อง Azure เพิ่ม `worldfert-azure.pub` เข้า `~/.ssh/authorized_keys`
3. เก็บ private key ไว้ที่ `deploy/cloud-vps/.local-secrets/` ซึ่ง **ไม่อยู่ใน git**
4. ทดสอบ `ssh -i ~/.ssh/worldfert-azure <user>@20.255.185.14 'echo OK'`

### ขั้นที่ 1 — สั่ง backup บน Azure

สั่งผ่าน 1433 ได้เลย ไม่ต้อง SSH

```sql
DECLARE @f nvarchar(4000) =
    N'C:\Backup\dbwins_worldfert9_' + CONVERT(varchar(8), GETDATE(), 112) + N'.bak';
BACKUP DATABASE [dbwins_worldfert9] TO DISK = @f
WITH COMPRESSION, CHECKSUM, INIT, STATS = 5;
RESTORE VERIFYONLY FROM DISK = @f;   -- ต้องผ่านก่อนถึงจะเอาไปใช้
```

> `CHECKSUM` กับ `VERIFYONLY` ไม่ใช่ของฟุ่มเฟือย — ไฟล์เสียที่เพิ่งมารู้ตอน restore
> แปลว่าเสียเวลาโอน 1 GB ไปฟรี ๆ และ B ก็ค้างอยู่ครึ่งทาง

### ขั้นที่ 2 — ดึงไฟล์ออกมา

```bash
scp -i ~/.ssh/worldfert-azure <user>@20.255.185.14:/path/to/dbwins_worldfert9_YYYYMMDD.bak /tmp/
sha256sum /tmp/dbwins_worldfert9_YYYYMMDD.bak > /tmp/dbwins_worldfert9_YYYYMMDD.bak.sha256
```

### ขั้นที่ 3 — ส่งขึ้น B

```bash
K=deploy/cloud-vps/.local-secrets/worldfert-hostinger-deploy
scp -i $K /tmp/dbwins_worldfert9_YYYYMMDD.bak     root@76.13.190.104:/srv/wf-transfer/incoming/mssql/
scp -i $K /tmp/dbwins_worldfert9_YYYYMMDD.bak.sha256 root@76.13.190.104:/srv/wf-transfer/incoming/mssql/
```

> ไฟล์ `.sha256` จำเป็น — `restore-mssql.sh` เรียก `verify-upload.sh` ตรวจก่อนเสมอ ไม่มีไฟล์นี้จะไม่ยอมรัน

### ขั้นที่ 4 — restore บน B

```bash
ssh -i $K root@76.13.190.104 \
  '/opt/worldfert/app/deploy/cloud-vps/server/restore-mssql.sh \
     /srv/wf-transfer/incoming/mssql/dbwins_worldfert9_YYYYMMDD.bak --confirm-replace'
```

สคริปต์จะทำให้เองตามลำดับ — **ห้ามสลับลำดับนี้เอง**

```
verify SHA-256 → ตรวจพื้นที่ว่าง ≥12GB → RESTORE VERIFYONLY
→ SINGLE_USER → RESTORE ... REPLACE, RECOVERY → MULTI_USER → RECOVERY SIMPLE
→ finalize-mssql.sh:
     CREATE LOGIN wf_reader / wf_owner
   → CREATE USER + db_datareader
   → run_migrations.js          ← ล้มถ้าไม่มี user มาก่อน (พิสูจน์มาแล้ว)
   → GRANT CONTROL/SELECT ON SCHEMA::wf
   → seed_admin.js
```

### ขั้นที่ 5 — ตรวจรับ

```bash
# 1) migration ต้องตรงกันทั้งสองฝั่ง
cd backend
DB_MODE=remote   node run_migrations.js --plan | grep unchanged
DB_MODE=remote_b node run_migrations.js --plan | grep unchanged
```

| ตรวจ | ค่าที่ต้องได้ |
|---|---|
| `run_migrations.js --plan` ทั้งสองฝั่ง | `unchanged: <n>; pending: 0; drift: 0` เลขเท่ากัน |
| `check_triggers_raiserror.sql` | `0` |
| recovery model | `SIMPLE` |
| จำนวน `dbo.SOHD` | **เท่ากันทั้งสองฝั่ง** |
| `/api/health` ของ B | `version` ตรงกับ A · `sqlserver: up` · `mysql: disabled` |
| เข้าแอป B ด้วยผู้ใช้จริง | เปิดใบสั่งขายเดือนล่าสุดได้ |

> ⚠ **`DB_MODE` เท่านั้น ไม่ใช่ `DB_TARGET`** — ตั้งผิดจะรันใส่ production โดยไม่เตือน
> ก่อนปล่อยให้เดินต่อ ต้องอ่านบรรทัด `Migration preflight for <TARGET>` ให้ตรงกับที่ตั้งใจ

## 5. ทำบ่อยแค่ไหน

| สถานการณ์ | ความถี่ |
|---|---|
| B เป็นตัวสำรองเฉย ๆ (ตอนนี้) | **เดือนละครั้ง** พอ — ให้ช่องว่างไม่เกิน 1 เดือน |
| เตรียมจะสลับไปใช้ B จริง | ทำ 1 รอบซ้อม แล้วทำอีกรอบก่อนสลับจริง |
| หลังสลับไปใช้ B แล้ว | **หยุดทันที** — ทิศทางจะกลับด้าน B → A |

**ทำระหว่างที่ไม่มีคนใช้ B เท่านั้น** ตอนนี้ปลอดภัยเพราะยังไม่มีใครใช้
วันไหน B มีผู้ใช้จริง ขั้นตอนนี้ **ใช้ไม่ได้อีกต่อไป** เพราะมันลบทั้งฐาน

## 5.1 ทางเลือกที่กำลังพิจารณาแทน — private network + VPN

เจ้าของระบบเสนอไว้ 3 ก.ย. 2569 ว่าอาจย้ายทั้งสองฝั่งไปอยู่ใน **เครือข่ายภายใน แล้วเข้าถึงผ่าน VPN**

**ทำไมทางนั้นแก้ปัญหาได้ตรงกว่า**

| ปัญหาในเอกสารนี้ | ทาง private network + VPN |
|---|---|
| ดึง `.bak` ออกจาก Azure ไม่ได้เพราะไม่มีคีย์ | อยู่วงเดียวกันแล้ว คัดลอกไฟล์ได้ตรง ๆ |
| ต้องเปิดพอร์ต 1433/3306 ให้ IP สาธารณะ | **ไม่ต้องเปิดสู่อินเทอร์เน็ตเลย** |
| IP ผู้ดูแลเป็น dynamic ทำให้ allowlist ค้างบ่อย | หมดปัญหา — ไม่ใช้ allowlist ตาม IP อีก |
| ต้องแจก SSH key ให้คนนอกทีม | ไม่ต้อง |

**สิ่งที่ต้องประเมินก่อนเลือกทางนั้น** — ยังไม่ได้ทำ

1. Azure VM ปัจจุบันย้ายเข้า VNet เดียวกับที่จะใช้ได้หรือไม่ หรือต้องสร้างใหม่
2. VPN แบบไหน (site-to-site ระหว่างผู้ให้บริการ หรือ client VPN ให้ผู้ดูแล)
3. Railway/Vercel เป็นบริการสาธารณะ — ยังต้องมีทางให้เข้าถึงฐานข้อมูลได้อยู่ดี
   ข้อนี้สำคัญที่สุดและอาจทำให้ทางนี้ใช้ไม่ได้ทั้งหมด ถ้ายังต้องคง PROD-A ไว้บน Railway
